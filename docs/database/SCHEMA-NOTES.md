# Database Schema Notes

> Companion to SRS §15 and [ERD.md](ERD.md). Describes how the schema is built, the rules enforced in SQL, and conventions developers must follow. Implemented in Phase 3 (2026-11-20).

## 1. Layout

| Path | Contents |
| --- | --- |

## 2. Workflow for schema changes

1. Edit the relevant `.prisma` file.
2. Generate a migration **without applying it** and review the SQL:

```bash
pnpm --filter @fos/db db:migrate --name describe_change
```

3. If the change needs a rule Prisma can't express (partial unique index, CHECK, trigger), append it to the generated `migration.sql`.
4. Apply locally, then confirm there's no drift between migrations, schema and database:

```bash
pnpm --filter @fos/db db:deploy
```

```bash
pnpm --filter @fos/db db:drift
```

5. Add a test to `packages/db/test/constraints.test.ts` for every new database rule. CI runs these tests on PostGIS and fails on drift.

**Never edit an applied migration** once it has been pushed. (The Phase 3 migrations were regenerated once before being pushed anywhere.)

Plain GiST/GIN indexes on columns are declared in the Prisma schema (`@@index(..., type: Gist|Gin)`) so Prisma knows about them. Partial and expression indexes live only in SQL; Prisma ignores them, so they don't cause drift.

## 3. Conventions

| Topic | Rule |
| --- | --- |
| Keys | UUIDv7, generated by Prisma (`@default(uuid(7))`) or by `uuidv7()` from `@fos/shared` for raw-SQL inserts. |
| Money | Integer paise. `Int` for bounded per-transaction amounts (orders, items, fees, refunds ≤ ₹2.1 crore); `BigInt` for accumulating balances and totals (ledger, settlements, payouts, analytics). Percentages are basis points (`*_bps`). |
| Time | `timestamptz(3)` everywhere; operating hours are `time` in the branch's `timezone`. `weekday` (operating hours, schedules) is **0 = Sunday … 6 = Saturday**; a slot whose `closes_at ≤ opens_at` crosses midnight. |
| Ratings | `rating_avg_bps` is the raw average in **hundredths of a star** (4.35★ = 435). The displayed rating is the Bayesian average of BR-REVIEW-007 (prior 4.0, weight 10), computed when reading. |
| Geography | `geography(Point|Polygon, 4326)` columns are `Unsupported` in Prisma. Models with a **required** geography column (`branches`, `customer_addresses`, `zones`, `order_addresses`, `delivery_locations`) cannot be created via Prisma Client; insert them with `$executeRaw` + `ST_GeogFromText(${'SRID=4326;POINT(lng lat)'})` in a repository. Reads via Prisma work but omit the geography column. |
| Raw SQL | Tagged templates only (`$queryRaw\`…\``); `$queryRawUnsafe`/`$executeRawUnsafe` are lint errors. |
| Deletes | References default to `ON DELETE RESTRICT` (required and optional). `CASCADE` only for pure child rows (join tables, options of a cart line, tokens of a session). Business entities are soft-deleted (`deleted_at`). |
| Enums | PostgreSQL enums for code-owned closed sets; lookup tables for admin-managed sets (cuisines). |

## 4. Rules enforced in SQL

### 4.1 Uniqueness (partial / expression indexes)

| Index | Rule | Requirement |
| --- | --- | --- |
| `users_email_active_uq`, `users_phone_active_uq` | One account per email/phone among non-anonymised users | BR-AUTH-014 |
| `refresh_tokens_one_active_per_session_uq` | One ACTIVE refresh token per session | FR-AUTH-022 |
| `customer_addresses_one_default_uq`, `customer_addresses_home_work_uq` | One default address; one HOME and one WORK | FR-ADDR-005, BR-ADDR-001 |
| `restaurant_bank_accounts_one_verified_uq`, `partner_bank_accounts_one_verified_uq` | One verified payout account | BR-REST-012 |
| `restaurant_members_live_uq`, `restaurant_members_one_owner_uq` | One live membership per user; one active owner | ADR-002 |
| `menu_categories_name_uq` | Category names unique per restaurant (case-insensitive) | FR-MENU-001 |
| `food_item_variants_one_default_uq` | One default variant | BR-MENU-004 |
| `food_item_customization_groups_uq` | Group attached once per item/variant | FR-MENU-007 |
| `carts_one_active_per_user_uq` | One active cart per user | BR-CART-001 |
| `coupons_code_live_uq` | Coupon codes unique (case-insensitive) | FR-ADMIN-060 |
| `payments_provider_order_uq` | One payment per provider order | FR-PAY-007 |
| `ledger_accounts_owner_type_uq` | One account per owner/type/currency | ADR-011 |

| `partner_vehicles_one_active_uq`, `partner_vehicles_registration_verified_uq` | One active vehicle; verified registrations unique | FR-DP-005 |
| `deliveries_one_active_per_partner_uq` | One active delivery per partner (MVP) | BR-DEL-014 |
| `delivery_assignments_one_accepted_uq`, `delivery_assignments_one_offer_per_partner_uq` | Exactly-once assignment; one open offer per partner | FR-DISP-006/007 |

| `ops_alerts_open_dedupe_uq` | One open alert per dedupe key | FR-ADMIN-002 |

### 4.2 CHECK constraints

Money non-negative and bounded (items ₹1–₹1,00,000, discounts below price, tips ₹0–₹500 in whole rupees, `payable = total − wallet`), `refunded ≤ captured ≤ amount`, wallet and cash-in-hand balances ≥ 0, non-zero ledger entries, rate fields 0–10000 bps, quantities 1–20, ratings 1–5, delivery radius 500–15000 m, prep time 5–90 min, customization `0 ≤ min ≤ max, max ≥ 1`, percentage coupons capped, coupon `used + reserved ≤ limit`, review target matches type, payout payee consistency, assigned deliveries have a partner, maker ≠ checker, failed orders have a reason, and formats (E.164 phone, pincode, GSTIN, FSSAI, IFSC, Aadhaar last-4). Names end in `_chk`; see the migration for the full list.

### 4.3 Triggers

| Trigger | Rule | Requirement |
| --- | --- | --- |
| `ledger_entries_balanced` (deferred constraint trigger) | Every journal transaction has ≥ 2 entries summing to 0 at COMMIT | DB-INT-004 |
| `*_append_only` (`fos_reject_mutation`) | No UPDATE/DELETE on ledger, order snapshots (items, options, price components, address, status history, cancellations, invoices), audit logs, consents, application reviews, branch status events, delivery status history, partner earnings, effective-dated configs | SRS §15.6, FR-AUDIT-002, FR-CFG-002 |
| `delivery_assignments_guard` | Offers freeze once final; only OFFERED → terminal and ACCEPTED → RELEASED/REVOKED; offer facts immutable | FR-DISP-013 |
| `payment_webhook_events_guard` | Payload immutable; processing status may change | FR-PAY-004 |
| `payment_attempts_guard` | Status progresses; payment, amount and provider payment ID immutable; no deletes | SRS §15.6 (v0.3.0) |
| `delivery_locations_no_update` | Trail points never edited (deleted only by retention) | SRS §20 |
| `zones_no_overlap` | ACTIVE zones may touch but not overlap | FR-ADMIN-070 |
| `branch_operating_hours_max_slots` | ≤ 3 slots per weekday | BR-REST-003 |
| `restaurants_search_vector`, `food_items_search_vector` | Weighted `tsvector` (name A, description C) via `unaccent` | ADR-009 |

**Redaction escape hatch.** Retention/anonymisation jobs (SRS §15.8, §20) may UPDATE append-only rows after `SET LOCAL fos.allow_redaction = 'on'` inside their transaction. DELETE remains blocked, and the audit log ignores the setting entirely.

## 5. How violations surface in Prisma (for the API error mapper)

| Violation | Postgres SQLSTATE | What Prisma throws | Suggested API code |
| --- | --- | --- | --- |
| Unique index (model call) | 23505 | `PrismaClientKnownRequestError` `P2002`, `meta.target` = fields (or constraint name for expression indexes) | `409` domain-specific conflict |
| Unique index (raw SQL) | 23505 | `P2010`, `meta.code = '23505'` | as above |
| Foreign key (insert/update) | 23503 | `P2003` | `409`/`422` |
| `ON DELETE RESTRICT` | 23001 | `PrismaClientUnknownRequestError` (no code; message names the constraint) | `409 CONFLICT` |
| CHECK constraint | 23514 | `PrismaClientUnknownRequestError` (message names `*_chk`) | `422` (indicates a missing service-level validation) |
| Trigger rule (append-only, overlap, ledger) | 23001 / 23P01 / 23514 | `PrismaClientUnknownRequestError` with the trigger's message | `409`/`500` (indicates a bug) |

The services validate first so users see specific messages; these database rules are the last line of defence.

## 6a. Read paths added in Phase 5

| Topic | How it works |
| --- | --- |
| Serviceability | `ST_Covers(zones.polygon, point)` finds the zone (an ACTIVE zone wins on a shared edge); discovery pre-filters branches with `ST_DWithin(location, point, LEAST(delivery_radius_m, zone.max_delivery_radius_m))` on the GiST index, in the same zone only. |
| Menu cache | Raw menu (categories, items, variants, options, availability rows, stock) cached in Redis under `menu:v2:{branchId}:{menu_version}` for 1 h. **Every write that changes a menu, availability or stock reaching 0 must increment `branches.menu_version`** (Phase 7–8 writers). Time-based state (branch open now, `unavailable_until` passed) is resolved per request, so it is never stale. |
| Search | Prefix full-text queries (`word:* & …`) on the weighted `search_vector`, with cuisine/category names added at query time as weight B. Typo tolerance uses `word_similarity(query, name) ≥ 0.3` (plain `similarity` scores a short query against a long dish name too low: "biriyani" vs "Chicken Dum Biryani" is 0.26). Trigram matches are used only when full text finds fewer than 5 dishes. User input is reduced to letters and digits before building the tsquery. |
| Geocode cache | `geocode_cache` keys: `rev:{provider}:{lat 4dp}:{lng 4dp}` (≈ 11 m cell), `place:{provider}:{id}`, `geo:{provider}:{sha256 of text}`; 30-day expiry. |

## 6b. Money paths added in Phase 6

| Topic | How it works |
| --- | --- |
| Ledger signs | Entries: **+ debit, − credit**; every transaction sums to zero (deferred trigger). `ledger_accounts.balance` is kept on the account's **normal side**: credit-normal accounts (customer wallet and hold, order liability, restaurant/partner payables, platform revenue, tax payable) store their credit balance as a positive number, so `balance >= 0` checks on wallets are meaningful. `LedgerService.normalSign()` is the single source of this mapping. |
| Ledger idempotency | `ledger_transactions (type, reference_type, reference_id, idempotency_key)` is unique; posting twice returns the first transaction. Accounts are locked in id order before balances change. JOB-LEDGER-001 (`LedgerService.verify`) compares every balance with its entries daily. |
| Wallet | Credits are lots (`wallet_credit_lots`, refund credits never expire, promo/goodwill 30 days). Order flow: HOLD (wallet → hold) at order creation, DEBIT (hold → order liability, consuming earliest-expiring lots) on payment, RELEASE (hold → wallet) on failure. |
| Payments | Each initiation adds a `payment_attempts` row; the provider payment id is linked when verify or a webhook names it (the attempt guard allows setting it once). Webhooks are stored raw in `payment_webhook_events` (unique per provider event id) and processed by the worker; status changes follow FR-PAY-009 precedence under a `payments` row lock. |
| Outbox | Payment and refund state changes write `outbox_events` in the same transaction (`payment.captured`, `payment.failed`, `payment.late_capture`, `payment.amount_mismatch`, `refund.succeeded`). The relay and the order transitions consuming them were added in Phase 7 (§6c). |
| Idempotency keys | `idempotency_keys (user_id, key)` hold the request hash and the stored response for 24 h; 5xx responses are not stored, so the client can retry with the same key. |
| Cart prices | `cart_items.unit_amount_seen` is the unit price the customer last saw (set on add/edit and when a checkout session is created); a different current price flags the line `PRICE_CHANGED`. |

## 6c. Order paths added in Phase 7

No schema changes in Phase 7; these are conventions the code relies on.

| Topic | How it works |
| --- | --- |
| Order status | Only `OrderTransitions.apply()` changes `orders.status`: it locks the row (`FOR UPDATE`), checks the expected version and the §10.3 rule for the actor, stamps the timestamp column, appends `order_status_history` and writes `order.<status>` to the outbox in the same transaction. |
| Outbox relay | Runs in the worker under a Redis leader lock (`outbox:relay:leader`, 15 s TTL). Events go to consumers in `sequence` order; when a consumer fails, later events of the same aggregate wait and `attempts` grows (ops alert after 5). Consumers must be idempotent: notifications use `notification_deliveries (event_id, user_id, channel)`; order reactions re-check state. Event types: `order.created`, `order.<status>`, `order.payment_pending`, `order.accept_reminder`, `payment.*`, `refund.succeeded`, `ticket.created`, `ticket.customer_replied`, `branch.auto_paused`. |
| Timers | BullMQ jobs on `orders` with ids `{job}-{orderId}` (BullMQ rejects a single `:` in custom ids). Handlers re-check the order first; JOB-ORD-007 re-creates missing timers every 5 min with the remaining delay. |
| Order money | Paid online and wallet money credits `CUSTOMER_ORDER_LIABILITY` (ORDER owner). Refunds before settlement debit it; a cancellation fee moves from it to `RESTAURANT_PAYABLE` (`CANCELLATION_FEE`); `ORDER_SETTLEMENT` empties it into restaurant payable, commission, fees, promo expense and tax payable, leaving only the tip for the partner settlement (Phase 9). |
| Cancellation quotes | `order_cancellations.quote_id` is derived (HMAC of order id, version, fee and refund, with the version in clear in the last group); nothing is stored before cancelling. |
| Invoices | One series (`FOS`) per financial year (IST, April–March); numbers are allocated under `pg_advisory_xact_lock(hashtext('invoice:FOS:<fy>'))` as max + 1, so they are gap-free. Issued on `order.delivered` or on first download. |
| Coupons on cancellation | `OffersService.release()` moves a redemption from RESERVED or REDEEMED to RELEASED and fixes `reserved_count` / `used_count` accordingly. |
| Notification templates | Version 1 of the defaults (`modules/notifications/catalog.ts`) is inserted into `notification_templates` on first use; the newest active version per key and channel is used. |

## 6d. Restaurant paths added in Phase 8

No schema changes in Phase 8.

| Topic | How it works |
| --- | --- |
| Applications | A restaurant row with `onboarding_status` is the application; its first branch is `PENDING_APPROVAL` until approval. The OWNER `restaurant_members` row exists from the start, but IAM only resolves memberships of restaurants that are `APPROVED` and `ACTIVE`. |
| Encrypted columns | `restaurants.pan_encrypted`, `restaurant_bank_accounts.account_number_encrypted`, `restaurant_change_requests.payload_encrypted`: `keyId(1) ‖ iv(12) ‖ tag(16) ‖ ciphertext` (AES-256-GCM, `platform/crypto.ts`). Keys come from `FIELD_ENCRYPTION_KEYS`; only `*_last4` is ever shown. |
| Files | `files.object_key` = `<purpose>/<yyyy-mm>/<id>.<ext>`; public images also have `<key>.thumb|card|hero.webp`. Status `UPLOADED` → `ATTACHED` when an entity claims it (owner and purpose checked) → `DELETED` when released or orphaned for 24 h. |
| menu_version | Bumped on every branch whose menu or status a write affects: menu structure (all branches of the restaurant), availability, status events, settings, hours, holidays, logo/profile. |
| Status log | `branch_status_events` is append-only; "closed for today" is a CLOSED row with `until`; the sweep picks the latest row by id (uuid v7 order). |
| Invitations | `restaurant_invitations.token_hash` = SHA-256 of a random token sent by SMS/email; accepted, revoked or expired after 7 days. |

## 6e. Delivery paths added in Phase 9

No schema changes in Phase 9.

| Topic | How it works |
| --- | --- |
| Presence | Redis, not the database: hash `partner:{id}:presence` (state, zone, last fix, break, offline-after-trip), GEO set `partners:zone:{zoneId}`, set `partners:online`, offer slot `offer-lock:partner:{id}`. `delivery_partners.last_location` is refreshed at most once a minute and is the fallback for tracking. |
| Location trail | `delivery_locations` rows (uuid v7 ids) are written for active deliveries only, sampled, plus every stage event; append-only per the Phase 3 trigger. |
| Dispatch | `delivery_assignments` holds every offer with its round, rank, score and `score_breakdown`; one OFFERED/ACCEPTED row per delivery at a time; acceptance locks the delivery and assignment rows. `deliveries.no_partner_deadline` drives the platform-fault cancellation. |
| Stage history | Every delivery transition writes `delivery_status_history` (with `flagged` for confirmed-outside-geofence arrivals) and an outbox event `delivery.<status>`. Failed OTP tries are `delivery_otp_attempts` rows and `orders.delivery_otp_attempts`. |
| Partner money | `partner_earnings` (one per delivery; base, distance, wait, surge, tip, total) mirrors ledger postings: `PARTNER_EARNING` (platform delivery cost → `PARTNER_PAYABLE`) and, keyed `tip`, the tip from the order's liability. COD collection debits `PARTNER_CASH_IN_HAND`. A payout = −`PARTNER_PAYABLE` balance − cash in hand. |
| Bank change | A new `partner_bank_accounts` row in `PENDING_VERIFICATION` beside the verified one (an older pending row becomes `SUPERSEDED`); payouts are held while one is pending. |
| Ratings | `rating_avg_bps` on `branches`, `restaurants` and `partner_stats` (hundredths of a star) and `rating_count` are recomputed from published, undeleted `reviews` by the `review.changed` consumer. One review per order per target is the Phase 3 partial unique index. |

## 7. Running PostgreSQL locally

- **Docker:** `pnpm infra:up` (PostGIS 16 on port 5432, plus `fos_test` and `fos_shadow`).
- **No Docker:** `infrastructure/scripts/local-postgres.sh init` starts a private PostgreSQL 18 + PostGIS instance on port **5433** with data in `.local/postgres` (requires `brew install postgresql@18 postgis` on macOS). Point `DATABASE_URL`, `TEST_DATABASE_URL` and `SHADOW_DATABASE_URL` at port 5433.

## 8. Deliberately deferred

- Monthly partitioning of `audit_logs`, `delivery_locations` and `notifications` is deferred until the DB-SCALE-001 thresholds (SRS §15.3, v0.3.0).
- ADV-only tables (chat, per-member permission overrides) are not created yet.
